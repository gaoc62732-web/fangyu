# 政区底图数据与渲染审计及改造建议

审计日期：2026-10-08  
状态：现状审计与方案提案；P1 交互渲染和前端内存第一阶段已实施，后续数据契约和更新流水线仍待实施。

## 审计结论

当前地图主路径已经使用 MapLibre 矢量瓦片，交互和个人记录仍以地区 UUID 为关联键；中国另有 OSM 下载、审核匹配、特殊边界修订、显示选项和瓦片构建等多条数据处理路径。主要问题不是单一渲染库太慢，而是显示数据和分析数据重复、全量几何在若干前端路径被载入、地区状态变化时逐地区更新渲染状态、Canvas 降级每帧绘制全部形状，以及生成物没有完整清理和一站式验收。

建议保留 Vue、TypeScript 和 MapLibre 的前端架构，先重新定义全世界稳定地区编号和几何数据契约，再把中国现有处理步骤收敛到可重复、可校验、可原子发布的一条流水线。是否更换离线几何处理语言应以代表性数据集的耗时和峰值内存基准决定；目前没有证据表明更换前端框架或语言能解决主要卡顿。

## 现状与范围

- `data/catalog/catalog.json` 有 3,999 个地区、17 个 scope；`data/catalog/manifest.json` 列出世界、中国及 15 个国家或地区几何文件。`world` scope 本身有 254 个地区。
- 地图主路径由 MapLibre 加载 `map-manifest.json` 中的省、市、县及境界瓦片；中国瓦片使用 PMTiles。PNG 导出、Canvas 降级和地理位置导入仍需要 GeoJSON 路径。
- 原始中国几何 `data/catalog/china.geo.json` 当前为 287,436,755 字节；生成目录中的 `geometry/china.geo.json` 为完整源几何副本。简化地图 `maps/china.json` 为 277,547,623 字节。中国边界选项 JSON 解压后 54,638,669 字节，发布 gzip 文件为 16,510,387 字节。
- 中国瓦片目录当前有 44 个 PMTiles、合计 1,501,638,631 字节。当前 manifest 引用 4 个、合计 141,120,886 字节；还有 40 个未被 manifest 引用的 PMTiles 和 2 个 `.tmp` 文件。发布配置将 `data/generated/web` 作为 Vite `publicDir`，所以未引用文件可能继续进入构建产物。
- 当前目录主键全是 UUID。全球同名核查按 Unicode NFKC 及空白、常见标点归一化后发现 28 组重名地区，因此名称只能用于校验和人工复核，不能独立承担主键。

静态检查确认的行为不等于浏览器性能测量。本次没有在目标设备上采集拖动、缩放、选中动画的帧时间或内存曲线；文中性能影响按代码路径和数据量列为风险，后续须用浏览器实测验收。

## 问题清单

### P1：交互渲染和前端内存

1. **每次外观刷新都对目录地区逐项设置 feature state。** `appearance()` 遍历当前 scope 的目录地区，对每个地区、每个非境界图层调用 `setFeatureState`；记录状态变化会触发这一路径。中国及县级图层下，更新量随地区和图层数相乘。应改为只更新状态有变化的地区，并在数据源 ID 已采用稳定地区编号后批量计算差异。中国边界选项图层也在外观更新时重设整套 GeoJSON source。
   证据：`apps/web/src/features/maps/use-tiled-map.ts:251`、`:329`、`:396`、`:635`、`:667`。

2. **Canvas 降级路径的帧成本与全国几何总量绑定。** 它将场景中所有 Feature 建成 `Path2D`，选择动画通过 `requestAnimationFrame` 推进；`draw()` 对全部形状重绘。缓存 Path2D 能减少路径构造，但不会减少每帧遍历和绘制的 Feature 数。政区模式下选中地图的动画时长为 650 ms；中国简化 GeoJSON 仍有约 278 MB。低配设备或 WebGL 降级时，这足以造成动画、拖动和缩放卡顿。
   证据：`apps/web/src/features/maps/use-tiled-map.ts:415`、`:455`、`:736`、`:777`，`packages/map-renderer/src/canvas-renderer.ts:166`、`:182`、`:229`、`:265`、`:385`、`:411`。

3. **几何和特殊边界数据有长生命周期、无显式缓存上限。** `ensureGeometry()` 将加载的每个 scope 几何保存在 store 的 `geometry` 中，没有逐 scope 释放或 LRU 上限；中国边界选项解压后会整体解析为 JS 对象并长期保留。连续浏览多个大 scope、切换地图或使用导入功能后，页面内存可能随已访问 scope 累加。gzip 减少网络体积，但不减少解析后的对象与坐标数组占用；解压、JSON 解析期间还会出现额外峰值副本。
   证据：`apps/web/src/app/store.ts:32`、`:38`、`:50`、`:64`、`:96`、`:105`。边界选项当前解压大小为 54,638,669 字节。

4. **地理位置导入会同步构造中国县级空间索引。** 用户进入相关导入流程时，页面加载中国几何和边界归属选项，然后在主线程创建 `CountySpatialIndex`；该索引遍历县级多边形、建立经纬度网格。此工作与全国全量坐标解析会占用交互线程，也会把导入专用的高精度数据留在全局 store。建议按需加载到 Worker，并将索引独立生命周期管理。
   证据：`apps/web/src/pages/ImportsPage.vue:70`、`:71`，`packages/import-export/src/spatial.ts:84`、`:98`。

### P1：存档和地区编号

5. **旅行记录快照以 UUID 为地区键，不能跨地区目录版本按名称识别。** 目前 JSON 导出的是完整 `RecordSnapshot`；其中 `regions` 是 `UUID -> VisitState` 字典。导入校验要求快照里的每一个地区 UUID 都存在于当前目录。目录主键变化或地区合并后，单独复制“点亮地区”既不直观，也不能用地区名称恢复关联。当前有完整 JSON/Excel 记录导入导出，但没有只导出点亮地区的 `{编号, 政区名}` 清单。
   证据：`apps/web/src/pages/ImportsPage.vue:206`、`:209`、`:225`，`packages/contracts/src/records.ts:95`、`:102`，`packages/domain/src/session.ts:54`、`:80`。

6. **现有地区 `code` 不满足直接作为全局地区主键的条件。** 目前 3,999 个地区的 `id` 全是 UUID。中国 3,250 个地区中有 16 个缺少 `code`；`710000` 被台湾省及其 20 个下属地区共同使用。北京东城区已有行政区划代码 `110101`，可以形成 `CN110101` 示例，但不能据此假定所有现有码唯一且永久不变。海外现有 `code` 体系并不统一，包括 ISO 三位国家码、日本两位码、`KR-11`、`FR-IDF`、`hcs:ABN`、`vn2025:lao-cai` 和源数据生成 ID 等。

   因此建议把外部行政代码与应用内部稳定编号分开保存。采用用户提出的 `国家/地区 alpha-2 + 六位数字` 作为展示及导入导出编号格式，例如 `CN110101`；中国可优先沿用有效且唯一的六位行政代码，缺码、重复码和将来新建地区由持久化分配表发号。海外六位数字由每国独立的不可复用分配表生成，外部代码另存为映射，不在行政代码变化时自动重编应用编号。

### P2：来源匹配、更新与数据发布

7. **OSM relation ID 参与下载和来源追溯，但不是所有地区的唯一匹配依据。** 下载脚本用 relation ID 获取 OSM 对象并在报告中保留引用；目录地区匹配还会比较名称/别名、admin_level、外部代码、父级范围、旧边界重叠和人工审核映射。国家轮廓也使用固定 relation ID。将来 OSM relation 重建或 ID 改变时，单纯依赖这些数字会造成获取失败或需要重新审核；不能简单描述为“当前应用只按 OSM ID 对边界”。
   证据：`scripts/fetch-osm-china-boundaries.py:230`、`:258`、`:276`、`:320`，`scripts/lib/prepare-osm-boundaries.mjs:112`、`:146`、`:164`、`:173`、`:220`、`:270`、`:286`。

8. **数据更新步骤分散，缺少贯穿来源抓取、特殊规则、瓦片生成和发布验证的单一入口。** 现有命令可以单独下载某省或全部省份、应用 OSM 几何、下载争议边界参考数据、运行中国边界政策、准备 Web 资源和打包快照；这些命令各自有用途，但没有一个从干净输入开始、执行全部规则、拒绝未匹配项、跑完整验收并原子更新快照/manifest 的可重复工作流。
   证据：`package.json:24`、`:27`、`:30`、`:31`，`scripts/fetch-osm-china-boundaries.py:348`、`:350`、`:354`，`scripts/prepare-web.mjs:20`、`:44`、`:417`、`:427`、`:432`，`docs/data-package-workflow.md`。

9. **中国例外处理是具体且有价值的业务规则，但目前分散在多份脚本中。** 已发现韩南/蔡甸分界、文登与环翠调整、唐古拉归属、历史地区剔除、港澳保留县级边界、岛屿/海岸线、争议边界参考数据及可切换的归属方案等处理。规则同时包含官方资料、人工审查与几何运算；如果只重新下载 OSM 并覆盖原几何，会丢失这些结果。应将每项作为版本控制的规则数据，记录输入证据、作用对象、输出哈希和审核状态，并把争议参考几何与默认显示面分开。
   证据：`scripts/prepare-china-boundary-policy.py:91`、`:95`、`:97`、`:99`、`:165`、`:174`、`:180`，`scripts/prepare-china-boundary-options.py:210`、`:305`、`:335`、`:359`，`scripts/lib/prepare-osm-boundaries.mjs:240`；快照分组见 `data/snapshots/groups.json`。

10. **版本化瓦片解决了正在打开的档案文件锁问题，但旧版本没有完整回收。** `prepare-web.mjs` 按内容版本生成 PMTiles 文件，并只删除一个旧目录；不同版本档案留在同一目录。此次实测有 40 个未被 manifest 引用的 PMTiles，占目录约 1.36 GB，另有两个临时文件。发布时复制整个 `publicDir`，会把这些无效旧档案带入部署。构建应写入干净 staging 目录，通过验收后原子替换，清理策略须在发布后保留当前版本和必要的回滚版本。
    证据：`scripts/prepare-web.mjs:339`、`:378`，`apps/web/vite.config.ts:67`。

11. **GeoJSON、简化 GeoJSON、瓦片和完整导入几何被多份生成。** 中国的源文件、供运行时读取的原几何副本、全层级简化图、按级别的简化图、PMTiles 和边界选项都包含重叠坐标。矢量瓦片主地图只需按视口获取瓦片；PNG 导出需要对应行政层级；地理导入需要分析精度。应明确划分三种数据产品，按功能懒加载，避免把所有产品一起作为前端可取用的静态目录发布。
    证据：`scripts/prepare-web.mjs:20`、`:44`、`:117`、`:128`、`:260`、`:282`、`:290`、`:415`、`:424`；数据实际体积见“现状与范围”。

12. **瓦片来源的简化和质量校验还没有形成全国/全球拓扑验收。** 简化逻辑逐 Feature 执行；相邻多边形没有基于共享弧段统一简化的保证，可能出现接缝、细缝或重叠。简化异常会回退原 Feature，可能无提示地放大输出。当前专项校验包含中国重点样本，但不等于所有相邻行政区和所有缩放级别均已通过拓扑验证。建议先在共享边拓扑上简化一次，再从同一拓扑生成各级别多边形和瓦片，并记录失败回退统计。
    证据：`scripts/prepare-web.mjs:260`、`:268`、`:282`、`:290`；中国专项样本校验：`scripts/verify-china-policy-assets.mjs`。

13. **地图资产验证脚本有过期契约。** 生成器当前中国 PMTiles `maxzoom` 为 12，但 `verify-map-assets.mts` 断言固定为 11；浏览器瓦片检查还查找不带版本号的 `county.pmtiles` 和 `province.pmtiles`，而 manifest 使用内容版本文件名。这会让正确的新资产被旧测试误报失败，或导致验证未真正覆盖当前引用资源。测试必须从 manifest 获取文件路径和 maxzoom，禁止在验收脚本重复硬编码。
    证据：`scripts/prepare-web.mjs:275`、`:290`、`:339`，`scripts/verify-map-assets.mts:51`、`:58`，`scripts/verify-tiled-map.mjs:51`、`:64`。

### P3：需要纳入设计和后续验证的问题

14. **地区名的规范化和层级信息应是匹配证据，不应被误认为唯一身份。** 当前地区有中文名、别名、父级及多个代码；重名组有 28 组。未来的本地映射表应以稳定编号为键，保留中英文名、别名、父级、层级、生效日期、退役日期及多个来源 ID；名称变化和同名不应自动产生新地区或合并记录。

15. **地图边界、旅行记录状态和行政区事实必须拆开版本。** 某地区更名、边界纠正、拆分、合并，不应让用户的历史到访记录被静默重置或套用到完全不同区域。数据需要有行政实体生命周期及可审核的 `supersedes`/拆分映射，个人记录应引用稳定编号。边界数据版本、地区目录版本和记录导出格式版本也应分别记录。

16. **来源许可及可复现性要按国家、图层和加工版本登记。** 现有中国 PMTiles 元数据包含 OSM ODbL 署名；当前数据包也能区分 runtime、osm-source 和 research。全球扩展时不能假定所有国家都来自 OSM 或使用相同许可。每个输入应记录来源 URL、下载时间/数据时间戳、许可、哈希、处理版本和人工复核项，并由发布检查阻止缺失许可或来源记录的数据进入 runtime。

17. **中国边界选项的体积与全量重建方式可能放大局部设置成本。** 目前选项包解压约 54.6 MB，地图载入中国 scope 时整体下载、解压和解析；显示方案变化会替换整个 GeoJSON source。建议拆成规则元数据、默认几何与用户实际启用的局部覆盖，只有必要方案才请求对应 patch。若决定保留整包，至少要把解码放到 Worker、测量峰值内存并设置可接受上限。

## 建议目标架构

### 地区身份与目录

- 建立唯一维护的全球 `region-id-registry`。应用地区编号格式为 `CCNNNNNN`，示例 `CN110101`；六位数字在该国家/地区命名空间内唯一、分配后不回收。地区退役后保留 tombstone，不把旧编号发给另一个实体。
- 对中国，先审定现行六位行政代码的唯一性；唯一有效的代码可直接形成 `CN` 编号。缺码/重复码地区由登记表分配保留号，并单独保存官方代码及历史值。台湾省和下属地区的现有 `710000` 冲突须先解决，不能批量拼接。
- 对非中国地区，应用编号由本地持久化序号表分配；外部行政代码（ISO 3166-2、政府代码、OSM relation、数据供应商 ID 等）是可多值且有来源的属性，不作为应用主键。按确定版本的全球目录一次性为已有目标地区分配编号，后续只追加、不排序重发。
- 建立 `source_feature_map`，每条关系记录 `regionId`、来源/版本/外部 Feature ID、名称匹配证据、层级、父级、空间覆盖检查和审核状态。OSM ID 只标识来源对象或获取地址，不能直接成为 app regionId。
- 记录行政实体有效时间、上级关系变化、别名及拆分/合并映射。导入导出依 stable ID 匹配，地区名用于展示及差异校验。

### 几何存储与生成

- 将高精度、经过审核的源边界作为独立数据集，和轻量目录元数据、个人记录完全分离；源数据按国家/数据版本分包，清单提供校验和和 provenance。
- 为下载归档、规范化边界、拓扑、派生展示几何、瓦片资产分层。建议规范化的分析几何存于 GeoPackage/FlatGeobuf 等按需读取格式或离线空间数据库；对共边简化和多层级生成使用支持拓扑的工具。最终具体容器由基准和维护成本决定。
- 中国和后续国家使用同一个流水线接口：`fetch -> normalize/CRS -> match stable IDs -> apply reviewed rules -> validate topology -> derive LOD -> build MVT/PMTiles -> verify -> publish manifest/package`。国家差异通过声明式来源和规则适配器表达，不复制整套脚本。
- 每次更新在临时目录完整生成。检查地区数、漏配/多配、几何有效性、共享边缝隙/重叠、父子包含、岛屿/飞地样例、许可证和文件哈希后，才原子切换 manifest；失败不改线上版本。
- 默认地图只取视口内 MVT；只在 PNG 导出时取选中层级的简化几何；地理导入按用户选择加载分析几何并放到 Worker。文件按访问需求分包和缓存，构建只发布 manifest 引用的档案。

### 渲染与内存

- 保留 MapLibre 矢量瓦片主渲染路径。将记录状态与地图几何解耦；只向当前已加载/可见的 Feature 写入差异状态，或用表达式从紧凑状态集合渲染。避免每次状态变化都遍历整个目录并对全部瓦片层重复设置状态。
- 把大边界选项数据切分成按规则/区域请求的 patch。常驻缓存设置容量和释放时机；切换 scope 后释放不再使用的高精度几何。为导出及导入 Worker 单独缓存，不复用到无期限的全局响应式 store。
- Canvas 降级只用针对当前层级的低精度、可视区域数据；对视口外 Feature 进行裁剪/跳过，按缩放级别限制路径复杂度。动画帧只重绘可见集合，记录交互变更不重建整套场景。若低配环境仍不能满足帧率，降级为短时或无动画，并尊重减少动态效果设置。
- 建立性能基线：记录首屏下载字节、边界选项解码耗时和峰值、交互帧时间 p50/p95、地图拖动时长、选择动画总耗时、切换多个国家后的 JS heap。对主流设备和 WebGL 不可用设备分别测试。

### 导入/导出

- 保留“完整旅行记录备份”和“点亮地区清单”两个用途清晰的格式。后者只包含用户明确选择的地区，至少导出 `id` 和 `name`；若选择保留目前的到访语义，再加 `state`。文件必须含格式版本、目录版本和国家代码，导入先按 ID 精确匹配、用名称做冲突校验，报告未知/退役/名称变更记录，再由用户选择合并或替换。
- 不要通过地区名直接模糊匹配并静默点亮；同名的 28 组证明此策略不安全。对于已经重命名但 ID 相同的地区可以继续匹配并提示名称不同。
- 将目录版本、用户快照版本、点亮地区文件版本分开；开发阶段可破坏旧格式，但新导出文件应明确 schema version，修改字段时有可测迁移或明确拒绝机制。

## 分阶段实施建议

1. **冻结当前基线与契约。** 保存中国现有默认边界、特殊规则和数据哈希；修正验证脚本改为读取 manifest；补足省市县、海岸、岛屿、飞地及重名地区样本。用浏览器采集卡顿和内存基线。
2. **先定义编号登记表与导入导出契约。** 在中国旧 UUID 到 `CN` 编号的迁移映射上处理缺码/重复码；为其他当前 scope 及全球计划纳入的地区预分配。批量重写目录引用、瓦片 `regionId`、记录键、边界修订规则和 fixtures。检查全局唯一率 100%、引用完整率 100%。
3. **把中国边界更新收敛成端到端 staging 流水线。** 下载固定数据快照；按稳定 ID 匹配 OSM/官方输入；重放特殊规则；生成并拓扑校验分析几何和显示几何；产出 manifest 与来源报告。干跑和正式应用使用同一代码路径。
4. **缩减运行时数据与地图更新成本。** 地图只打包 manifest 当前引用瓦片；按需求获取各层级几何；状态渲染改成差分或可见 Feature 更新；边界选项拆分；Canvas 走 viewport + LOD。
5. **扩展全球国家。** 在身份登记表稳定后逐国家加入来源适配器、地区匹配报告和质量样例。每个国家先通过来源许可、层级定义、覆盖率、编号及拓扑门槛，再成为可导入导出的正式地区集。

建议验收门槛：地区 ID 在全球 100% 唯一且长期不复用；当前边界目录所有 Feature 都映射到一个稳定地区或显式标为非行政边界；源几何和生成资产可由哈希复现；共享边拓扑测试无未解释裂缝/重叠；全量更新脚本能从干净 staging 一步运行且失败不发布；用户切换至少 10 个国家后内存有上限；在目标设备拖动/缩放 p95 帧时间达到产品确认的预算。性能数值应在实际设备基线后设定。

## 语言与工具选择建议

不建议仅为地图问题替换 Vue/TypeScript 前端。当前中国几何离线处理已经使用 Python 与 Shapely 类 GIS 工作流，前端空间索引、全量绘制和数据缓存才是已看到的主要风险。先减少前端必须解析的数据并把空间计算移出主线程，收益比迁移语言更直接。

离线流水线可以先统一成 Python 编排、使用成熟 GEOS/GDAL 几何操作，再保留或替换现有 Node 瓦片构建器；也可以用 Rust 实现经基准证明确实耗时的单个热点。比较时使用同一批全国/全球代表数据，记录 wall time、峰值 RSS、输入输出哈希、拓扑错误数和开发依赖成本。更换语言本身不应被当作性能目标；如果现有 Node `geojson-vt`/PMTiles 构建速度足够，减少重复几何和修复资产清理更重要。

## 已确认决策

以下选择由项目负责人于 2026-10-09 确认，后续设计与实现按此执行。新的决策问题仍应先在聊天中给出证据和选项，得到答复后再补记于此处。

### D1. 地区编号方案：选项 C

采用国家/地区二字码加六位数字作为正式地区编号。中国优先使用唯一、有效的行政区划代码；缺码、重复码或代码变化不能保持身份时由项目登记表分配稳定编号。海外使用项目分配的内部六位编号，来源代码单独保存。编号一经分配不回收、不因名称排序变化而重发。

### D2. 编号命名空间：选项 B，并明确港澳台规则

按 ISO alpha-2 作为国家/地区命名空间基础，但香港、澳门、台湾统一使用 `CN` 前缀，并分别使用 `71`、`81`、`82` 号段；同一行政层级内的完整六位数字必须唯一。其他国家使用对应二字码加内部指定的六位编号，例如英国伦敦可采用 `GB110100`，后六位由项目分配，不要求对应当地官方代码。地图 scope 与编号命名空间分开维护。

### D3. 全球初始化范围：选项 C

先为全球国家/地区层建立编号，再按国家逐步加入下级行政区。新增国家和层级沿用对应命名空间的持久化编号表，不重新排序或重发既有编号。

### D4. 点亮地区导入导出：选项 B

建立独立地区清单，保留地区编号、政区名和原始到访状态；导入时提供合并或替换。编号负责匹配，政区名用于显示和核对。完整旅行记录备份继续作为另一种用途。

### D5. 全球边界来源：选项 A，并允许有名的本地补充包

OSM 作为全球通用边界来源，国家差异、特殊行政关系和争议地区由本地规则修正。OSM 不提供的特定边界可直接采用项目已有本地数据，不强制迁移到 OSM；这类数据包要有明确、稳定的命名。例如南海九段线使用独立的本地命名图层/数据包。争议地区的本地规则由项目负责人决定。

### D6. 几何处理语言与瓦片构建器

几何处理采用能最快完成目标的语言和工具；瓦片构建器第一阶段保留现有实现。若替换瓦片构建器，应在方案中列出替代选项及其收益、代价和迁移范围供项目负责人决定。

### D7. 特殊边界原则与审批

特殊边界和例外规则由项目负责人直接决定；项目负责人发现原则遗漏时会另行告知。当前不额外引入外部证据或来源进行印证和审批。实现时保留可追溯的本地规则与命名数据包，但不自行改变已确认的边界原则。

## P1 第一阶段实施记录（2026-10-09）

本阶段只处理“交互渲染和前端内存”四项，不实施编号登记表、OSM 更新流水线或点亮清单格式改造。

- **地图状态更新**：`use-tiled-map` 为 feature state 建立页面级差异缓存；重复外观刷新不再重复提交相同状态。政区只写入其实际所属的矢量层（中国按省/市/县分层），不会再对每个地区乘以全部层级提交状态。中国边界选项 GeoJSON source 仅在规则设置变化时替换，线覆盖层仅在规则或显示级别变化时替换。
- **Canvas 降级渲染**：场景点位在 `setScene` 时预计算投影；绘制阶段按当前视口跳过不可见形状和点位，拖动通过 `requestAnimationFrame` 合并绘制，高频 hover 命中检测也合帧处理。边界框来自发布 manifest，缺失时仍回退到原有路径计算。中国降级地图按当前行政级别请求对应简化文件。
- **前端几何生命周期**：移除 Pinia 中按 scope 长期保留的原始 GeoJSON 缓存。中国边界选项数据改为引用计数生命周期，地图组件卸载或离开中国 scope 后释放解压后的对象。
- **导入空间索引**：中国几何、边界规则应用、`CountySpatialIndex` 构建和点/线命中计算移入页面级 Worker。主线程只接收地区编号命中结果；导入页卸载或规则设置变化时终止 Worker，避免索引和高精度几何跨页面常驻。
- **特殊边界切换**：特殊边界 GeoJSON 首次建立后，开关切换只通过 MapLibre `updateData` 提交新增、删除或几何确实变化的 Feature；普通同类政区不会重复提交几何。更新请求串行排队，等待普通矢量源和特殊源都稳定后再显示覆盖层；增量更新失败时自动回退到最新完整 FeatureCollection，避免快速切换或跨省几何更新后出现空白。

本阶段新增 feature state 差异、Canvas 视口/合帧、空间索引 Worker 生命周期和边界包引用计数测试。当前验证为 Vue 类型检查通过，`@fangyu/map-renderer` 与 `@fangyu/import-export` 类型检查通过，Prettier 检查通过，Web Vitest 全部 15 个测试文件、89 项通过。

Canvas 降级仍会解析当前层级的整份简化 GeoJSON：目前中国省、市、县文件分别约 42.5 MB、85.5 MB、155.8 MB；因此本次降低了视口内 Path2D 构造和逐帧绘制成本，但没有消除首次下载/JSON 解析的峰值内存。继续将降级数据拆成可按需读取的小包或二进制空间索引，应作为该 P1 的后续工作。当前未在真实浏览器/GPU 设备上采集拖动、缩放帧时间和长时间 JS heap 曲线。

本次用同一运行时包做了可复现的 Node 内存测量（`apps/web/dist/maps/china-boundary-options.json.gz`，仅保留解析后的对象以观察常驻成本）：压缩读取后 RSS 约 60 MB，解压缓冲阶段约 169 MB，JSON 解析峰值约 397 MB，主动 GC 后仍约 295 MB（JS heap 约 159 MB）。这不是浏览器/GPU 峰值，但说明完整选项包解析会产生远高于压缩文件体积的瞬时开销；后续拆分规则包或改用二进制/按需读取格式仍有明确收益。当前 Edge 未开放 CDP 调试端口，因此本轮无法从你已启动的标签页读取真实 JS heap 曲线。

### 特殊管理区的跨模块要求

特殊管理区必须同时存在于边界更新、目录编号和点亮清单设计中，不能只作为地图显示补丁。当前至少包括苏州工业园区、深汕特别合作区、呼中区/新林区、加格达奇区、松岭区、连江县（金马相关岛屿方案）、金门县和唐古拉山镇西藏管理区。以苏州工业园区为例：开关开启时它拥有独立几何、独立点击和独立显示；开关关闭时几何并入虎丘区，但该管理区的稳定身份、名称和历史记录不能因此消失。

后续边界更新脚本应先按稳定地区身份载入这些管理区，再应用本地裁切、合并和虚线等规则，并在报告中分别记录“独立显示几何”和“关闭时合并几何”。编号登记表应为管理区分配可长期保留的独立编号，同时保存其法定父级、显示开关、关闭时合并目标及规则版本。点亮地区清单导入导出应导出管理区本身的编号和名称；导入时按编号恢复其记录，不把关闭开关误解为删除或改写该地区的身份。当前 P1 只落实了渲染时序与增量更新，编号登记表、更新流水线和点亮清单格式仍按后续阶段处理。
