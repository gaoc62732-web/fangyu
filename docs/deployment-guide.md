# 方舆新手上线指南

本文按当前仓库结构说明怎样先发布一个任何人都能打开的版本，以及怎样继续升级为带账号和云端存储的服务。上线是把应用放到公网并持续运行；它不会自动让本机浏览器里的记录变成云端数据。

## 1. 先选上线目标

| 方式                   | 用户能做什么                             | 需要的服务                                             | 当前状态                                                   |
| ---------------------- | ---------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------- |
| 公共演示版（建议先做） | 任何人打开地图，在自己的浏览器里记录旅行 | 静态网站托管                                           | 前端已有 demo 模式；每个人的数据留在自己的浏览器中         |
| 多用户账号版           | 登录后跨设备保存个人记录                 | 静态网站、Node API、PostgreSQL + PostGIS、域名和 HTTPS | 服务端模式已有基础，但公开注册、账号找回和生产运维还未完成 |

当前账号注册默认关闭。服务端模式只能由站点维护者通过命令创建账号，不能直接面向公众开放注册。不要让所有访客共用一个账号：账号内的个人记录会混在一起。

## 2. 项目由什么组成

- `apps/web` 是 Vue 3 + Vite 前端。构建后是可交给静态主机的文件，地图、专题与公共目录由浏览器加载。
- `apps/api` 是 NestJS/Express API，提供目录、登录、个人记录和存档接口。Better Auth 管理登录会话，PostgreSQL 保存认证数据与个人 JSON 记录。
- `packages/*` 是前后端共用的类型、目录、领域逻辑、地图绘制和导入导出代码。
- 公共地图和目录数据本体不在 Git 中。小型 `data/snapshots/current.json` 与 `groups.json` 固定数据版本和打包规则，必须随代码提交，干净克隆才知道该下载哪些数据；其他地图源文件仍由数据包恢复。`pnpm build` 会生成并复制前端所需的地图资源。
- `infra/docker-compose.yml` 只用于本地启动 PostgreSQL + PostGIS，不是完整生产部署配置。

当前数据快照的 runtime 与 research 压缩包合计约 525 MiB；网页构建脚本会为地图生成派生资源并预留 8 GiB Node 内存。初次构建应使用有足够磁盘空间和内存的电脑或 CI 机器。

## 3. 发布公共演示版

这是目前最简单、风险最低的公开试用方式。演示版不需要 API、数据库、账号密钥或 `.env`；访客的记录存放在各自浏览器中。清除浏览器数据或换设备不会自动同步，用户仍可使用应用里的备份/恢复功能。

1. 安装 Node.js `22.12` 或更新版本，克隆仓库后在项目根目录安装依赖。安装脚本会使用仓库锁定的 pnpm `10.15.0`，首次运行需要网络；它也会在本机补齐被 Git 忽略的 `.env` 文件，这些文件不要上传：

   ```sh
   node scripts/install.mjs
   ```

   后续 `pnpm` 命令请确认 `pnpm --version` 是 `10.15.0`。若系统的全局 pnpm 版本不同，可用 `node node_modules/pnpm/bin/pnpm.cjs` 代替命令开头的 `pnpm`。

2. 下载并校验构建需要的公共数据：

   ```sh
   pnpm data:sync -- --group runtime --group research
   pnpm data:verify -- --group runtime --group research
   ```

   如果自动下载失败，按[获取开发数据](data-download.md)从 GitHub Release 下载对应附件，再用 `--directory` 指定附件目录。数据包不含个人记录或密钥。

3. 显式以 demo 模式构建，避免把服务器模式误打进网页：

   ```sh
   # macOS / Linux
   VITE_APP_MODE=demo pnpm build
   ```

   PowerShell 可执行：

   ```powershell
   $env:VITE_APP_MODE = 'demo'
   pnpm build
   Remove-Item Env:VITE_APP_MODE
   ```

4. 把 `apps/web/dist` 目录发布到任一支持 HTTPS 的静态网站托管服务。若使用项目子路径托管，构建前设置 `VITE_PAGES_BASE` 为带首尾斜线的路径，例如 `/fangyu/`；发布到域名根目录则使用 `/`。

5. 打开 HTTPS 地址，检查首页、地图瓦片、目录搜索、记录保存与导出，并在手机屏幕上快速走一遍。地图底图可能访问第三方服务；上线前核实其可用性、访问配额、署名和许可。地图样式许可证见 `apps/web/src/features/maps/styles/LICENSE.osm-liberty.md`。仓库目前没有集中完整的数据来源/许可清单，旧文档引用的 `docs/data-notices.md` 文件不存在；公开发布前需补齐并核验每类数据的再分发条件和署名要求。

每次修改前端或公共数据后都要重新构建和发布。切勿把 `.env`、数据库备份、个人浏览器存档或账户密码放进静态网站。

## 4. 升级为账号与云端存储

在演示版稳定后，再准备正式域名、Linux 主机或容器平台、支持 PostGIS 的 PostgreSQL 17 数据库，以及 HTTPS 反向代理。建议让网页和 API 使用同一个域名：反向代理将 `/api/` 转给 API 的 3000 端口，其余请求交给 `apps/web/dist`。这样浏览器访问 `/api/v1` 同源，部署配置更简单。

1. 先在与正式环境相同的 Node `22.12+` 环境安装依赖，恢复并校验 runtime/research 数据。API 运行时也必须带有 `data/catalog` 和 `data/manual/china` 源数据；网页的 `apps/web/dist` 不能替代 API 所需源文件。

2. 在平台的密钥管理界面设置 API 环境变量。不要把真实值提交到 Git：

   ```text
   HOST=0.0.0.0
   PORT=3000
   WEB_ORIGIN=https://你的域名
   BETTER_AUTH_URL=https://你的域名
   BETTER_AUTH_SECRET=至少32字符的随机密钥
   DATABASE_URL=平台提供的PostgreSQL连接地址
   ```

   `DATABASE_URL` 必须指向可启用 PostGIS 的数据库。密钥可用 `openssl rand -hex 32` 生成。`WEB_ORIGIN` 与 `BETTER_AUTH_URL` 写浏览器实际使用的 HTTPS 根地址，不要加 `/api/v1`。API 默认只监听本机地址；容器或独立主机经反向代理访问时要设置 `HOST=0.0.0.0`，同时不要把数据库端口公开到互联网。

3. 在构建时设置 `VITE_APP_MODE=server`、`VITE_API_BASE_URL=/api/v1`，然后运行仓库根目录的完整生产构建。这两个 `VITE_` 配置会写入公开网页，不能放秘密：

   ```sh
   # macOS / Linux
   VITE_APP_MODE=server VITE_API_BASE_URL=/api/v1 pnpm build
   ```

   ```powershell
   # PowerShell
   $env:VITE_APP_MODE = 'server'
   $env:VITE_API_BASE_URL = '/api/v1'
   pnpm build
   Remove-Item Env:VITE_APP_MODE, Env:VITE_API_BASE_URL
   ```

   将 API 与 `apps/web/dist` 一起部署，按同源规则配置 HTTPS 反向代理和 SPA 静态文件服务。

4. 对空数据库执行一次表结构初始化，再创建维护者账号：

   ```sh
   pnpm db:migrate
   pnpm create-user
   ```

   `create-user` 会提示显示名称；密码通过 `FANGYU_ACCOUNT_PASSWORD` 提供，至少 12 位。不要把密码写进命令历史或仓库文件。首次上线前，应在测试数据库先完整演练迁移和账号登录。

5. 启动 API：

   ```sh
   pnpm --filter @fangyu/api start
   ```

   托管平台通常直接注入环境变量，不会提供 `apps/api/.env`；API 脚本已允许该文件缺省。健康检查地址为 `https://你的域名/api/v1/health`，现在会执行一次数据库查询，数据库不可用时返回 HTTP 503。

6. 从正式域名登录，新增一条测试记录，刷新页面并重新登录确认数据仍在；确认另一个账号（如已有）看不到这条记录。再检查备份/恢复、HTTPS Cookie、日志与数据库备份能否恢复。

不要把 `apps/api/src/admin-main.ts` 作为公网服务启动，也不要向公网代理其管理路由。它是供本机维护目录的服务。普通公开 API 已经与这组文件管理接口分开；更新公共目录应走受审查的数据发布流程。

## 5. 地图资源和性能评估

**结论：目前不需要更换 MapLibre、PMTiles 或 PostgreSQL 等技术栈，但正式上线要认真选择静态资源托管。**主地图已经预先生成矢量瓦片，MapLibre 按当前地图视图读取瓦片；中国边界以 PMTiles 档案提供，正常看地图不需要先把全部原始边界下载到浏览器。地图流量应由支持 HTTP Range 的静态主机或 CDN 承担，不应经过 NestJS API 和 PostgreSQL。

本机当前生成的 `data/generated/web` 有 954 个文件、约 1,021 MiB；其中 `tiles/` 约 103 MiB、`maps/` 约 566 MiB、`geometry/` 约 349 MiB。它们承担的任务不同：

- 中国四份 PMTiles 档案合计约 99 MiB，最大的县级档案约 58 MiB。客户端根据视图、缩放和显示层级发起范围请求；静态主机需要正确返回 HTTP `206 Partial Content` 和 `Content-Range`。访客不会因为打开首页就下载整个档案。
- 中国特殊边界选项压缩后约 7.9 MiB，解压 JSON 约 26.2 MiB、含约 99 万个弧线坐标点。打开中国地区地图时会完整下载并解析这份补充数据，而且当前代码会在创建地图前等待它完成；弱网首屏有进一步优化空间。地点地图会等首屏绘制后再加载。它补充的是少量特殊边界方案，不是全部县区面的来源。
- `geometry/china.geo.json` 约 278 MiB，用于导入地理文件时在后台 Worker 建立县区空间索引；该导入功能会请求并处理整份中国原始几何。它不属于普通看图的首屏请求，但低速网络或低内存设备上的大文件导入仍可能较慢。
- `maps/` 中的大份简化 GeoJSON 用于 Canvas 回退和地图图片导出，不是常规矢量地图的首屏数据。

上线时按以下方式处理：

1. 选允许发布约 1 GiB 静态文件、支持大文件和 HTTP Range 的静态托管/CDN。对 `/tiles/` 的 PMTiles 路径不要启用会改变字节偏移的整文件压缩；用浏览器网络面板抽查 PMTiles 请求是否返回 `206`。若把资源放到独立域名，还要配置 CORS 并暴露 `Content-Range` 等响应头。
2. `map-manifest.json` 和 `maps/china-boundary-options.json.gz` 使用固定文件名，部署时应让它们重新验证或不长期缓存；带内容版本号的瓦片 URL 可设长期不可变缓存。避免对所有静态文件一刀切设置永久缓存。
3. 当前前端使用同一个 Vite `BASE_URL` 拼接应用和地图资源地址，没有独立 CDN 域名配置。初次部署建议让应用与这些文件同源，或通过同域名反向代理把瓦片路径转到对象存储；改为跨域 CDN 前先补统一的资源基址配置并验证 CORS/Range。
4. 上线后用无缓存浏览器和普通手机网络测地图首开、缩放、重新访问和导入大文件的耗时/内存。当前测得的是本机生成文件大小，没有公网、移动设备或高并发基准。

后续优化优先考虑把中国特殊边界选项的下载推迟到地图首屏可用后，以及为线路/地理导入提供压缩、分区或预索引的空间数据。如果之后要发布更多国家的超精细边界，优先考虑更细的预计算瓦片和延迟加载。只有当边界要频繁在线更新、需要按用户请求动态空间查询，或静态瓦片流量/更新流程难以承担时，再评估 PostGIS 动态 MVT 服务。用户量增加本身不要求地图换成数据库渲染；对象存储/CDN 通常更适合分发固定版本的地图数据。

## 6. 开放公众注册前还要补什么

当前项目还不能作为完整的自助注册服务直接运营。开放注册前至少需要完成：

- 注册、邮箱验证、密码重置、账户停用/删除和用户支持流程。当前 API 默认禁用注册，只有维护者能创建账号。
- 登录与注册限流、滥用防护、密码尝试告警、会话退出与密钥轮换流程。
- 隐私政策与数据删除/导出承诺，说明邮箱和旅行记录保存在哪里、保留多久、如何删除。服务端记录属于个人数据。
- 正式环境可重复的部署配置、错误监控、数据库自动备份及恢复演练。当前 Compose 文件只有本地数据库，没有 Web/API 容器或反向代理。
- 编号化数据库迁移和升级回滚方案。现有迁移脚本适合初始化当前版本，不应假定 `CREATE TABLE IF NOT EXISTS` 能升级未来结构。
- 多用户并发与隔离、登录 Cookie、断网/数据库故障、记录冲突、真实设备和公网资源路径的端到端测试。
- 公共数据和底图服务的许可、署名、服务配额及大陆网络可达性核实。若主要面向中国大陆用户，域名和主机的备案要求也要提前确认。

此外，当前发布说明明确记录了全工作区类型检查未通过，服务端真实数据库、真实账号和公网部署尚未验收。发布正式版本前先修复并通过 `pnpm check`，再在隔离的测试数据库完成以上验收；不要把“构建成功”当作“生产环境已验证”。

## 7. 发布前检查清单

- [ ] 从已审阅的提交/tag 构建；确认 `git status` 中没有未提交改动。
- [ ] 确认数据快照清单与 runtime/research 附件对应，且 `pnpm data:verify` 通过。
- [ ] 按发布目标设置 demo/server 模式；server 模式的 `VITE_` 配置修改后重新构建网页。
- [ ] 不公开 `.env`、密钥、初始密码、数据库端口或本机管理 API。
- [ ] 正式域名使用 HTTPS；反向代理正确转发 `/api/` 并保留 Cookie 所需的请求头。
- [ ] 备份数据库，演练一次还原，并用真实浏览器验证记录保存、重新登录和数据隔离。
- [ ] 检查数据来源/地图署名、许可、第三方底图配额和目标用户地区的访问情况。
- [ ] 抽查地图清单缓存、PMTiles 的 HTTP Range 响应，并在普通移动网络下完成冷启动检查。
