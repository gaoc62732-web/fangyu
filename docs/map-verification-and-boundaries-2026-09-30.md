# 天地图接入、地图检查与边界数据方案

检查日期：2026-09-30。本文补充并更新 `uiux-implementation-2026-09-30.md` 中的地图验收状态。

## 本地配置

浏览器密钥已写入 `apps/web/.env.local` 的 `VITE_TIANDITU_KEY`，该文件被 Git 忽略。报告、代码及测试不记录真实密钥。Vite 开发服务重启和生产重新构建后生效；发布环境需要单独配置相同环境变量。

## 已发现并修正的问题

1. **地图容器高度为零。** MapLibre 的 `.maplibregl-map { position: relative }` 与应用 `.map-surface` 选择器优先级相同，开发环境的样式加载顺序使后者失效。画布只有默认高度且被容器裁掉，看起来整张地图空白。增加应用容器选择器的明确优先级，实测画布恢复为地图工作区尺寸。
2. **省界被重复绘制。** 原始中国数据的 `border` 层包含 34 个粗省级 Polygon/MultiPolygon 和 10 个 LineString；它不是纯粹的国界线层。粗轮廓又叠在正式行政边界上，造成交叉和分叉。WebGL 过滤掉这 34 个粗轮廓，仅保留独立线要素；Canvas 降级采取相同规则。保留正式行政边界及地区 ID，不改原始地理匹配源。
3. **加载完成后瓦片错误不提示。** 现在边界资源失败在首次加载之后也显示错误，并保留“使用简化地图”“重试地图”入口。
4. **异步地图切换的过期结果。** manifest 在校验当前初始化代次后才写入，旧降级请求不能改写新地图的错误／加载状态；重建地图清理悬停状态和旧 Canvas 实例。
5. 天地图栅格源设置 1—18 级请求范围，超过其最高级别后使用已有瓦片，避免随应用无限缩放请求不存在的高级瓦片。线帽和折角使用圆角，仅改善线条连接，不冒充提高几何精度。
6. **首屏分类清单空白。** 行在布局完成前被测为零高，虚拟列表缓存零高后反复补偿偏移，内部偏移变成 676px，而实际 scrollTop 仍为 0。零高测量现在回退到该行估算高度，不让隐藏／未布局状态污染尺寸缓存。实际浏览器重新加载后首项从“世界遗产”正常显示，补充异步首屏布局回归测试。

## 边界不平滑的三层原因

### 1. 两套不同精度的轮廓叠画——已修正

| 地区   | 原 `border` 粗轮廓点数 | 正式省级轮廓点数 |
| ------ | ---------------------: | ---------------: |
| 北京市 |                     93 |              271 |
| 天津市 |                    100 |              247 |
| 河北省 |                    549 |            1,428 |

点数包含环闭合点。两个轮廓不能通过改变线宽变成相同边界。当前修复排除了这项人为干扰。

### 2. 瓦片过度放大——尚未重建数据管线

当前世界最高 z3，省级 z5、市级 z6、县级 z7，extent 为 4096。MapLibre 放大后继续使用这些级别的数据，不会自动增加细节。

按 512 CSS 像素的矢量瓦片计算，一个量化格在显示缩放 `z` 下约为 `512 × 2^(z - sourceMaxZoom) / extent` 像素。省级 z5 数据放到 z12，一个格约 16px；z14 约 64px。即使源边界共边，量化台阶也会很明显。

不能只把 extent 改成非常大的数：本版本 MapLibre 在加载几何时还会缩放、取整到内部 extent 8192。需合理提高最高**数据**缩放级别，同时匹配生成器和 PBF 编码的 extent，不能只改清单中的 maxzoom。

建议把 z14 作为首轮边界精度验收上限，目标额外量化误差不超过约 1px；例如数据 z10、extent 8192 是可评估的起点。街道更近的缩放可以保留底图与项目，边界精度上限应明确。实际值需结合数据和传输量测量。

### 3. 原始数据及独立简化——需要数据质量处理

现有东城区原始多边形只有 12 个点。重新切瓦片最多保留这些点，不能恢复已经丢失的弯曲细节。不要用样条插值、模糊或人为加点伪造真实边界。

中国正式省级数据中，北京—河北有 257 条完全相同的共享线段，江苏—安徽有 327 条，说明至少这些样本的原始共边基础是存在的；这不是全国拓扑合格证明。

普通逐 Polygon 简化可能给相邻面保留不同节点。尤其 Canvas／PNG 当前采用逐要素 Turf 简化，依然需要改为共享弧段只简化一次。检查省、市、县之间的层级一致性时，不应未经校验就用县界聚合覆盖全部省界，以免改变原目录口径。

## 天地图是否能直接提供边界

### 行政区划 V2.0：可以直接调用，精度有限

[官方文档](https://lbs.tianditu.gov.cn/server/administrative2.html) 提供：

```text
GET https://api.tianditu.gov.cn/v2/administrative
    ?keyword=156110000&childLevel=0&extensions=true&tk=<浏览器密钥>
```

支持名称或行政区划编码。`extensions=true` 返回 `boundary`（WKT MULTIPOLYGON），另有 `gb`、`name`、`level`、`center`。转换为 GeoJSON 后，可作为 MapLibre 数据源选中、填色和描边。不要把 center 当作项目坐标，也不要假定 childLevel 返回的每个子级都包含轮廓。

用本次密钥在浏览器从本地测试源实际调用，三次均 HTTP 200、业务 status 200，跨域可读：

| 地区   | 现有原始点数 | API 返回点数 | WKT 字符数 |
| ------ | -----------: | -----------: | ---------: |
| 北京市 |          271 |          423 |      8,815 |
| 东城区 |           12 |           19 |        413 |
| 河北省 |        1,428 |        2,206 |     45,846 |

点数更多不代表位置更准确。东城区 19 点已经表明它是概化轮廓；接口没有按 zoom 请求更精细轮廓的参数，也没有文档承诺的街道尺度精度。可以用于按选中地区加载高亮，不能保证所有相邻面同版本、严格无缝或任意放大保持细节。

该密钥为浏览器类型：Node 直接调用得到权限类型错误，而真实浏览器调用成功。不能把浏览器密钥硬搬到构建脚本／服务端，也不能把 Node 403 误判为密钥失效。

### 官方可视化 GeoJSON：优先抽样的候选

[天地图行政区划可视化](https://cloudcenter.tianditu.gov.cn/administrativeDivision/) 提供按区域、省／市／县选择的 GeoJSON 下载。2026-09-30 页面显示：数据更新时间 2025 年 9 月、局部数据更新、仅供地图可视化使用。

本轮确认了下载入口和说明，尚未下载该数据做质量对比。它与 API 是否相同精度、共同边是否一致、现有地区编码能否完整映射，需要以文件为准。可视化用途也意味着不应顺带替换精确地理匹配数据。

### “全球境界” WMTS：可叠加，但不能承担记录填色

[地图服务文档](https://lbs.tianditu.gov.cn/server/MapService.html) 有 `ibo_w`（球面墨卡托）和 `ibo_c`（经纬度）境界图层。它们可作为境界视觉叠加，但返回的是服务已经绘制好的瓦片，不能据此获得每个地区的 Polygon 与稳定记录 ID，也不能按个人到访状态单独填色。文档没有证明它覆盖方舆所需的全部省市县级境界，不应把“全球境界”理解为完整县界数据。

同样，`vec_w` 名称中的“矢量底图”不能等同于可直接编辑的 MVT 几何接口；本应用接入的是栅格底图。

## 是否改用 OpenStreetMap

OSM 的行政区边界可提取为可叠加几何，关系及共享 way 结构有利于共边；一些地方细节会更多，但不能预设中国各省市县都更完整、更新、更准确。本轮 OSM 文档站访问超时，未获取样本，不对它作全国覆盖承诺。

需要额外处理 `boundary=administrative` / `admin_level`、闭环和飞地、关系缺件、不同地区层级口径、数据版本，以及 OSM relation ID 到方舆稳定地区 ID 的映射。不能只按名称覆盖。其数据采用 ODbL；署名和派生数据库的许可责任应一并评估，具体分发方式决定要求。参考 [OSM 版权与许可](https://www.openstreetmap.org/copyright)。

不建议前端每次查看地区都向公共 Overpass 请求大范围边界。正式使用应获取版本化快照、校验后自行服务；OSM 的数据开放不等于公共查询／瓦片服务提供无限容量。

## 推荐路线与验收

1. 继续使用天地图道路与地名底图，保留已经修正的单套行政边界显示。
2. 先对天地图可视化下载版与现有原始数据做同范围比较：京津冀接壤、东城区、长三角多省交界、海岸与岛屿、飞地。若其精度仍不足，再引入有明确来源和日期的更精细官方数据／OSM 样本。
3. 固定几何来源与版本，建立外部编码到现有 regionId 的映射。统一坐标基准；明确验证 WGS84／CGCS2000／GCJ-02，不能因选了 Web Mercator 就认为自动消除了坐标偏移。
4. 建立共享边拓扑，统一简化，共边绘制一次；选中描边单独控制。显式区分行政区面、共享线、独立境界符号，弃用含义混杂的 border 层。
5. 生成多级精度 MVT。小范围先继续用静态 MVT；高精度级别使文件数显著增加时评估 PMTiles。PMTiles 是同类瓦片的静态打包／按需读取方式，不增加源数据精度；需验证部署站支持 HTTP Range、缓存和 CORS。
6. 显示瓦片、Canvas 降级和 PNG 使用同一个经过校验的显示用几何来源。原精度地理导入匹配源保持独立。

验收需同时检查：稳定 ID 无缺失；共享边缝隙／重叠；多部件和孔洞；相邻瓦片接缝；z5/z8/z10/z12/z14 同位置截图；不同省／市／县级别切换；底图叠合；区域选择和到访填色；传输量与首屏请求；PNG 和降级是否重现裂缝。用同一显示范围量测误差，不能只比较“点数更多”或肉眼更圆滑。

当前建议是“天地图底图 + 自己控制版本的行政边界”，先验证天地图 GeoJSON，再决定是否引入 OSM。直接 API 高亮可作为过渡能力；全国足迹填色与导出更适合版本一致、预先校验的边界集合。
